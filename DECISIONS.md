# DECISIONS.md — решения, принятые самостоятельно при сборке Jarvis

Формат: решение → почему → чем можно поправить позже, если не подойдёт.

## 1. Spec Kit CLI не использовался
`specify init --here --integration claude` зависал на интерактивном промпте в
неинтерактивной среде (TUI-выбор без stdin). По правилам `/allforme` при
недоступности Spec Kit — сформулировал `spec.md`/`plan.md` вручную тем же по
структуре текстом. Ничего не потеряно по содержанию, просто без CLI.

## 2. Wake word: Porcupine → openWakeWord, фраза "Jarvis" → "hey jarvis"
Research-фаза нашла: бесплатный tier Picovoice Porcupine закрыт 30.06.2026
(подтверждено официальной цитатой Picovoice), постоянное некоммерческое
использование больше недоступно бесплатно. Заменено на open-source
openWakeWord (MIT/Apache, без access key). Побочный эффект: у openWakeWord
нет pretrained-модели под голое "Jarvis", только под фразу **"hey jarvis"**
("Хей, Джарвис") — принято как компромисс, а не заблокировано, т.к.
обучение кастомной модели явно вне scope v1 (см. `spec.md`). Если позже
захочется голое "Jarvis" — нужно либо обучить свою модель под openWakeWord
(вне текущего scope), либо вернуться к Porcupine на платном тарифе.

## 3. Модель для tool-calling: `qwen3:8b`
Ни `gemma4:2b`, ни `gemma4:26b` не оптимальны для основного диалога
(маленькая слаба, большая не помещается в 12GB VRAM целиком). Research
зафиксировал `qwen3:8b` (5.2GB, нативный tool-calling, лидер по стабильности
tool-calling среди локальных моделей на 2026 год по BFCL-бенчмаркам) —
прописано в `config/config.yaml`. Резерв, если качество русского не устроит:
`qwen2.5:7b-instruct`. `gemma4:26b` оставлен как отдельный режим "глубокого
анализа" по ключевым словам (см. `brain/ollama_client.py::_select_model`).

## 4. Сборка с нуля, а не форк готового репозитория
Research не нашёл ни одного репозитория, реально закрывающего архитектуру
целиком (Porcupine/openWakeWord + faster-whisper GPU + Silero + Ollama
tool-calling + Windows автозапуск одновременно). Самый популярный кандидат
не обновлялся год и тянет лишний LangChain; самый свежий Windows-специфичный
имеет всего 7 звёзд — недостаточно доверия для security-критичного проекта
(белый список действий, физический запрет опасных операций). Решено собирать
по `plan.md` с нуля, точечно подглядывая паттерны у кандидатов из
`RESEARCH.md`.

## 5. OLLAMA_MODELS не перенесён на диск D автоматически
Перенос ~25GB уже скачанных моделей C→D — потенциально долгая (I/O) и слегка
рискованная (нужно останавливать/перезапускать Ollama) операция для
автономного прогона без возможности пользователя подтвердить в моменте.
Вместо переноса — в `README.md` даны точные PowerShell-команды для
самостоятельного переноса перед `ollama pull qwen3:8b`. Модель `qwen3:8b`
запущена на закачку в фоне в текущем сеансе БЕЗ переноса (уйдёт на диск C,
~5.2GB) — если пользователь перенесёт `OLLAMA_MODELS` на D позже, модель
нужно будет либо переставить (`ollama rm` + `pull` заново после переноса),
либо перенести файл вручную вместе с остальными.

## 6. Barge-in реализован через переиспользование wake-listener'а
Вместо отдельного детектора голоса поверх TTS-плеера, повторное срабатывание
того же wake word во время `speaking_event` трактуется как сигнал прерывания
(`interrupt_event.set()`), а не как новая команда. Следствие: чтобы отдать
новую команду после прерывания, нужно **сказать wake-фразу второй раз**
отдельно (два отдельных "Хей, Джарвис", а не "Хей, Джарвис, стоп" одним
выдохом) — задокументировано в `MANUAL_TEST.md`, сценарий 5.

## 7. Личность/громкость/трей — 3 состояния, не больше
Трей-иконка поддерживает только idle/listening/thinking (нет отдельного
"speaking") — во время озвучки ответа состояние остаётся "thinking". Решено
не усложнять до 4 состояний ради MVP; при желании можно добавить "speaking"
как отдельный жёлто-другой цвет одной строкой в `service/tray.py::_COLORS`.

## 8. Найденный и исправленный при живом тесте баг: кодировка консоли
`python orchestrator.py --text` в консоли Windows брал stdin/stdout в
кодировке по умолчанию (не UTF-8), из-за чего кириллический ввод портился
ДО отправки в Ollama — модель получала мусор вместо текста и отвечала
невпопад (проверено вживую: запрос "Удали все файлы" без фикса дал ответ
не по теме). Исправлено в `orchestrator.py::_force_utf8_console()` —
принудительный `reconfigure(encoding="utf-8")` для stdin/stdout/stderr при
старте. После фикса тот же запрос дал верный явный отказ. Это же годится и
для реального использования в PowerShell/cmd с нестандартной кодовой
страницей.

## 9. web_search: реально протестирован, есть нестабильность соединения
Прогон с `qwen3:8b` вживую подтвердил: `run_safe_command("git status")` и
явный отказ на удаление файлов работают правильно end-to-end (не только в
моках). `web_search` в этой тестовой сессии дважды получил обрыв/таймаут
соединения к `html.duckduckgo.com` (сначала generic User-Agent — заменён на
реалистичный Chrome UA, — потом Read timed out при timeout=10с). Не
исключено, что это сетевая особенность текущей среды тестирования, а не
баг кода — сама функция корректно ловит ошибку и не падает. Пользователю
стоит проверить `web_search` на своей машине; если DuckDuckGo регулярно
блокирует — можно поднять `tools.web_search.timeout_seconds` в
`config.yaml` или сменить источник поиска.

## 10. Расширение доступа: весь диск D + установка пакетов/программ + self-restart
По явному запросу пользователя ("хочу полный доступ к диску D, устанавливать/
улучшать себя, если я скажу") добавлено, после предупреждения о рисках и
явного подтверждения пользователем (выбраны все три пункта):

- `tools.allowed_roots` расширен с `D:\claude code prj` до всего `D:\` —
  `read_file`/`write_code_file`/`open_explorer` теперь работают с любым путём
  на диске D. Диск C по-прежнему недоступен. Функции удаления как не было,
  так и нет — расширение затрагивает только чтение/запись существующих
  путей.
- Новый инструмент `install_package(name)` — `pip install <name>`, имя
  проверяется маской `_SAFE_NAME_RE` (буквы/цифры/точки/дефисы/подчёркивания/
  плюсы, без пробелов и shell-метасимволов) ДО вызова subprocess, без
  `shell=True`, argv-список. Худший сценарий при ошибке распознавания речи —
  установка не того или несуществующего пакета (обратимо).
- Новый инструмент `install_app(name)` — то же самое через `winget install
  --id <name> -e --accept-package-agreements --accept-source-agreements
  --silent` (официальный менеджер пакетов Windows, не сторонние источники).
- Новый инструмент `restart_self()` — перезапускает процесс ассистента через
  2 секунды в отдельном потоке (чтобы TTS успел ответить), используется
  после того, как ассистент сам отредактировал свой код через
  `write_code_file`. `write_code_file` и раньше технически мог писать в
  папку `jarvis` (она была внутри старого allowed_roots) — новым является
  именно возможность самому перезапуститься, чтобы изменения применились.
- Тест `test_dangerous_names_never_registered` обновлён: `restart_self` явно
  вынесен в исключения (перезапуск ПРОЦЕССА ассистента — не компьютера),
  остальные "опасные" подстроки (`shutdown`, `reboot`, `delete`, `format`,
  `uninstall` и т.д.) по-прежнему проверяются на отсутствие в реестре.
- Системный промпт (`brain/personality.py`) явно предупреждён: использовать
  install_package/install_app/restart_self ТОЛЬКО когда пользователь явно
  попросил, не по своей инициативе.
- Добавлены юнит-тесты (`tests/test_tools.py::TestInstallPackage`,
  `TestInstallApp`, `TestRestartSelf`) по тому же паттерну, что и
  `run_safe_command`: валидное имя → subprocess вызывается с argv-списком
  без shell; попытка инъекции (`&&`, `;`, `|`, пробелы, backticks, path
  traversal) → subprocess НЕ вызывается вообще. 92/92 теста проходят.
- **Осознанный риск, не устранённый полностью**: голосовое управление
  установкой/самоизменением кода — по сути мощнее, чем исходная модель
  угроз "белый список из безобидных действий". Смягчается тем, что (а) имя
  пакета/программы жёстко валидируется, инъекция через голос невозможна;
  (б) сама установка/правка кода всё ещё обратима (не как `del`/`format`);
  (в) это явный осознанный выбор владельца своего личного ПК, а не действие
  над чужой/production-системой.

## 11. Добавлен хоткей Numpad "+" как альтернатива голосовому wake word
Пока пользователь диагностирует, почему голосовой wake word не реагирует
(зависимости/AirPods-микрофон), добавлен `wake/hotkey_listener.py` —
глобальный хоткей (по умолчанию Numpad "+", библиотека `keyboard`,
настраивается в `config.yaml -> hotkey.key`). В `orchestrator.py` оба
источника (`WakeWordListener` и `HotkeyListener`) зовут один и тот же
`on_wake()`, поэтому barge-in и вся остальная логика работают одинаково
независимо от способа активации. Оба потока проверяются на "жив ли поток"
через 3с после старта — если `keyboard` не установлен или не хватает прав
для глобального перехвата клавиатуры, это будет явно видно в логе, а не
тихо "просто не реагирует".

## 12. Текстовый ввод добавлен параллельно голосу/хоткею (не отдельный режим)
Пользователь диагностирует, почему голос не реагирует, и попросил "на
всякий" добавить текстовый ввод. Вместо переключения на `--text` (у него нет
трея/wake word/хоткея) добавлен `stdin_fallback_reader()` — фоновый поток
внутри обычного `python orchestrator.py`, читающий строки из той же консоли.
Очередь активации (`trigger_queue`) теперь несёт либо `None` (голос/хоткей —
ещё нужно записать+распознать речь), либо готовую строку (текст с
клавиатуры — сразу в `brain`, без STT). Если stdin недоступен (скрытый
процесс без консоли, автозапуск через Планировщик) — поток тихо
самоотключается и логирует это, не мешая голосу/хоткею.

## 13. Что реально не проверено (честно)
Ни один компонент голосового пайплайна (wake/stt/tts) не запускался на
реальном железе в рамках этой сборки — только статический код-ревью,
`py_compile` и юнит-тесты с моками (`tools`/`brain`). Причины: сборка шла в
неинтерактивной среде без реального доступа к микрофону/колонкам этой
машины из-под агентов, и тяжёлые ML-зависимости (torch/faster-whisper/
openwakeword) не устанавливались (риск долгой закачки при ограниченном
времени сессии). `python orchestrator.py --text` — единственный путь,
реально проверенный (и то не до конца — см. финальный отчёт).
